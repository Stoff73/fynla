How Fyn Thinks

Two maps of the assistant behind Fynla — what it is made of, and what happens in the seconds after someone presses send.

Written for a non-technical reader Reflects the system as built, August 2026

The one idea to hold on to

Everything below is a consequence of a single design decision.

Fyn looks like one chat window, and to the person using it, it is one assistant with one personality and one memory. Underneath, Fyn runs in two states, and the difference between them is not personality — it is permission.

The guidance state answers questions. It can read everything about the user and can run every calculation the app owns, but it is physically incapable of changing a single record. The tools that write to the database are removed from its toolbox before it is ever asked a question, and a second check rejects them again at the moment of use.

The capture state is the only part of the system that ever enters or edits information. It runs onboarding, and it handles every “add my new ISA” moment afterwards.

When someone in the middle of a conversation asks Fyn to save something, the guidance state hands the turn to the capture state, the record is written, and the reply comes back in the same breath. The user never sees the handover. No badge changes, no mode switch, no second window. That invisibility is deliberate, and it is tested.

One assistant to the user. Two states to the system. The line between them is a permission boundary, and it is enforced by machinery rather than by asking the model nicely.

What the model actually does — and what it never does

It is worth being precise about this, because it is where most misunderstanding sits.

The model decides
What the person meant, which of the available tools to reach for, and how to word the reply.
The model never decides
Whether it is allowed to write. Whether the user has enough data on file to be given advice. What a tax allowance is. What a recommendation is. Those are all settled before or after it is asked.
The numbers
Come from the app’s calculation engines and the tax rulebook, handed to the model as results. The model narrates them; it does not compute them.
The write
Is performed by application code after the model names a tool. The code re-checks for duplicates, validates the values, and can refuse.

Map two: one message, end to end

The same system, viewed as a journey. Four checks apply to everything; then the path forks by what the message actually is.

Three journeys, in full

The same three tracks, walked step by step with a real sentence at the top of each.

“I’ve got a workplace pension with Aviva, worth about £40,000.”

Track A · During onboarding

  1. fixedConsent, budget and the one-turn lock clear. The routing test finds this person mid-flow with a saved step, so the turn belongs to the capture state.
  2. fixedThe script says the current step is the open-ended pensions question. Most steps are buttons or a single value and are answered without any AI. This one is not.
  3. modelFyn is handed its standard instructions, the facts already known about this household, and only the tools for recording pensions. It reads the sentence and names one: create a pension, provider Aviva, workplace, £40,000.
  4. fixedBefore anything is written, one rule checks whether a matching pension already exists. Update it, ask about it, or create it — that decision is made in code, in one place, for all twenty-odd record types.
  5. savesThe record is written. The screen is told a pension was created and which page it lives on, so the confirmation can link straight to it.
  6. fixedFyn reads the entry back — provider, type, value — and offers to correct it. Every single piece of data entered gets this treatment; it is not reserved for the ones we thought were risky.
  7. fixedNet worth, retirement projections and the risk profile recalculate on their own, triggered by the record appearing.
  8. fixedThe script advances to the next step and asks the next question. The whole turn is written to memory and sealed into the audit chain.

Model calls: one. Everything else was fixed rules.

“Add my new stocks and shares ISA — £8,000 with Vanguard.”

Track B · Months after setup, mid-conversation

  1. fixedThe routing test sends this to the guidance state, because setup is complete. The guidance state cannot write. On its own that would be a dead end.
  2. fixedBefore any AI is involved, a pattern check reads the sentence as a save: an action word plus a record type. This deliberately does not depend on the model behaving well.
  3. fixedA duplicate check runs against their actual accounts. If they already had this ISA, Fyn would say so in plain words — written by code, not the model, so it can never accidentally imply something was saved when it was not.
  4. handoffThe turn is handed to the capture state. This is the only crossing of the permission boundary in the system, and the user sees nothing: no mode badge, no second message, no change in the input box.
  5. modelNow holding write tools, Fyn names the record: investment account, stocks and shares ISA, Vanguard, £8,000.
  6. savesApplication code validates the values, applies the duplicate rule again, and writes the account. Ownership, tax wrapper and contribution tracking are set from the values given.
  7. fixedThe reply confirms what was saved and where it now lives. Recalculation, memory and audit follow as always.

If the pattern check at step two misses, the model itself raises the same handoff mid-answer and lands in exactly the same place. Two doors, one room.

“Am I saving enough for retirement?”

Track C · The guidance state, read-only throughout

  1. fixedThe question is classified as retirement readiness. That single label decides what happens for the rest of the turn: which data is required, which engine runs, and how much context to assemble.
  2. gatefixedThe readiness gate checks the required list for that topic — date of birth, income, expenditure, a retirement target. If any is missing, Fyn says exactly what it needs and points at the page to add it. It will not produce an answer built on assumptions.
  3. retrieveWith the gate passed, context is assembled fresh: who they are, their financial position, what data is still thin, and the facts Fyn already holds so it never re-asks. Relevant rules are pulled from the written library by keyword and filtered to the current tax year.
  4. retrieveLive figures are fetched, not remembered. Fyn holds a pointer to “this user’s retirement plan” and follows it at the moment of asking, so the number quoted is the number the app would show on screen right now.
  5. modelA short planning call decides the next move — answer now, or retrieve more first. It is capped, so a turn can never spiral.
  6. engineThe retirement engine runs and returns the actual analysis: projected pot, shortfall, contribution headroom. Fyn is explicitly instructed not to invent recommendations — it uses what the engine calculated.
  7. modelThe answer streams out, shaped by the six-step method: check the data, fetch current figures, analyse the position, recommend specific actions with amounts, explain how to act, and signpost regulated advice.
  8. fixedThroughout, no write tool exists on this turn. Had one somehow been named, a second check would have rejected it at the point of use and logged the attempt.

If they reply “OK, put my contribution up to £600 a month”, the turn leaves Track C and joins Track B at step two.

The four memories, in plain terms

“Memory” is doing four different jobs in this system, and conflating them causes most of the confusion.

What Fyn knows
A written library of UK tax rules, allowances, product characteristics and Fynla’s house view, authored deliberately and version-controlled. It is searched by keyword rather than by similarity — a simple approach chosen on purpose, and sufficient at current scale. Facts carry dates, so a question about a past year gets that year’s answer.
How Fyn works
Written procedures describing how to handle a situation, including the onboarding script itself. Only the procedures relevant to the message load into a given turn, which keeps the assistant focused rather than drowning it in instructions.
What happened
Every turn is written out in full — the instructions given, the context assembled, the tools used, the result. Past turns can be recalled into a later conversation. This file is also the compliance record: it is what lets anyone reconstruct why Fyn said what it said on a particular day.
What we know about you
Merged from four sources in strict order — the saved record first, then what was volunteered earlier in this flow, then this conversation, then earlier conversations. Later sources only fill gaps; they never override the record. This is the machinery behind “Fyn doesn’t ask me the same thing twice”.

A fifth kind, deliberately switched off

Fyn can also propose new facts it has learned about a specific user, and propose amendments to its own procedures. Neither is applied automatically. Both queue for human review, and the whole pipeline is off by default in production. Nothing Fyn learns changes how Fyn behaves without a person approving it.

Where the guardrails actually are

Regulated financial guidance needs its safety to be structural. Asking a model to behave is not a control.

Read-only means read-only
Write tools are removed from the guidance state’s list before the turn begins, and a separate check rejects them again at the moment of use. Two independent mechanisms, one shared definition of what counts as a write.
No advice without data
Each topic has a required-data list. Fyn stops and says what is missing rather than filling gaps with assumptions.
No invented numbers
Tax values come from one configured source; analysis comes from the engines. Neither is written into the assistant’s instructions, so neither can drift or go stale in the prompt.
No false confirmations
When a record already exists, the acknowledgement is generated by code, not by the model — so “you already have this” can never be phrased in a way that sounds like “saved”.
Nothing outside remit
Non-financial questions are declined by a rule before the model is ever consulted.
Consent is live
Checked at the door and re-checked every couple of seconds while a reply is streaming. Withdraw consent mid-answer and the answer stops.
Tamper-evident record
Each audit entry is hashed together with the one before it, so the chain can be walked and any alteration located. It cannot be quietly edited after the fact.
Bounded by design
Planning steps are capped, retrieval is capped, queued messages are capped, and locks expire on their own — so a conversation cannot spiral or wedge.

Where this is heading

The two states already share one instruction set, one turn loop, one memory system and one set of write handlers. What still differs is which tools each is handed. The direction of travel is to collapse them into a single Fyn whose permissions are decided entirely at the moment a tool is reached for — which is already how the safety check works today.

For a stakeholder, the practical point is that this is a consolidation, not a rebuild. It removes a seam; it does not change what Fyn does, what it remembers, or where the guardrails sit.
