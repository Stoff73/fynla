03Which Fyn answers: the dispatch predicate

One prompt, two write states. The state is chosen per request by a single predicate, shared by sendMessage, streamQueuedMessage and action (AiChatController.php:268, :445, :925). It is not keyed on onboarding_completed alone.

  • routesToOnboarding(conversation, user) ConversationModeResolver.php:12–29
    • config onboarding.fyn_flow_enabled === false → advice (read-only), always :14–16
    • conversation.metadata.source === 'surface_action' → advice, immutable :19–21
    • conversation.metadata.source === 'fyn_onboarding' → onboarding director, immutable :23–25
    • (onboarding_completed === false OR active_campaign !== null) AND onboarding_fyn_step !== null → onboarding director :27–28
      • step nulled by a "Something else" pause → advice, even mid-onboarding or mid-campaign (fail-safe: no step context, no write state)

Where the campaign marker is set. Only POST /api/ai-chat/onboarding/start stamps active_campaign, when from= resolves to a campaign_map entry (AiChatController.php:750–812, config/onboarding.php:79–86). Both campaigns enter at base_work, not at an intro state. It is cleared at the campaign terminal and on the pause.

The planner, model call 1

Only now is a model consulted, and only to route (FynLoop.php:191–295). It sees the last 6 turns truncated to 600 characters each, the full procedural corpus, the user's recalled episodes, and returns exactly one plan tool call from a closed vocabulary. reason and ground both run the same reasoner; retrieve is a no-op that re-plans up to 3 times; learn writes an episode (or stages a fact or procedure amendment when learning is enabled) and re-plans; no_action yields the canonical defer line. A provider failure degrades to reason so a planner outage can never kill a turn (Planner.php:84–95).

08Where recommendations come from

Fyn does not invent recommendations. The prompt says so twice and the wiring makes it so: the ranked list and the composed plan are computed by deterministic engines, then handed to the model as text (in <financial_context>) or as tool results. The model's job is to select, explain and voice them by claim tier.

One ranking (Batch B, 9 September 2026). PriorityRanker is the home: the seeded label sets the band (critical 95, high 85, medium 60, low 45), the benefit figure and the module weight only break ties inside it. CoordinatingAgent (Fyn's <financial_context>, get_recommendations, the holistic plan) and RecommendationsAggregatorService (the web API, dashboard cards, /m next actions) both call it; the aggregator's own 85 / 60 / 45 map, the second module-weight table in CoordinatingAgent, TaxOptimisationAgent's urgency map and the five adapters' label resolvers are gone. /m next actions sort by the same score rather than by the pound benefit. Verified for the young family persona: the web dashboard Savings tab, /api/recommendations/top, the /m top actions and Fyn's ranked block (ai_messages 439) list the same items in the same order.
