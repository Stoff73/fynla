### A trap worth recording: the identity probe must omit cookies

Re-testing `/m` after the income change, the strip did not render although the API returned `strip: "pa_taper"` when I called it from the page. I nearly raised this as a `/m` rendering defect. It was not one. The `/m` app was still signed in as Persona B, and `/m` rendered Persona B's payload correctly.

What misled me was the identity check itself. Fetching `/api/auth/user` from the page with an `Authorization` header still sends the same-origin session cookie, and `auth:sanctum` answered the cookie, which was Persona A's desktop session, not the bearer. The probe reported Persona A while the page was serving Persona B. Confirming the token ids on the server settled it: the `/m` token belonged to user 417. Repeating the fetch with `credentials: 'omit'` returned Persona B, matching the page.

The `verify-m` skill's rule to establish the account from `GET /api/auth/user` rather than from `localStorage` needs this addition: send the bearer with cookies omitted, or the cookie session answers instead.

## Defects found

### 0. The Gift Aid flag is silently discarded on save — FIXED in `fd60af65d`

Severity: silent data loss, reaching well beyond this slice. Confidence: high, verified at the request, the response and the database.

The expenditure form is the only surface in the app that exposes a Gift Aid toggle. On save it posts `{"is_gift_aid": true}` to `PUT /api/user/profile/personal`, which answers 200 with "Personal information updated successfully" and returns a user whose `is_gift_aid` is still false. The database agrees: user 416 holds `is_gift_aid` false alongside `annual_charitable_donations` 12000.00.

The cause is a validation rule that disagrees with the field the form posts. `UpdatePersonalInfoRequest` carries no `is_gift_aid` rule, so `$request->validated()` at `app/Http/Controllers/Api/UserProfileController.php:108` discards it before the service sees it. The only rule for the field is in `app/Http/Requests/UpdateIncomeOccupationRequest.php:46`, on an endpoint this form never calls. The write is at `resources/js/components/UserProfile/ExpenditureForm.vue:2345`, whose own comment records that this same call destroyed data once before.

Nothing signals the loss. The request succeeds, no error surfaces, and re-opening the form shows the box still ticked because the component keeps its local state. Every Gift Aid calculation downstream, the band extension and the higher-rate relief strategy, therefore runs as though the user does not claim it.

This blocked both Step 4 regressions, which cannot be observed without a Gift Aid figure. Fixed by adding the rule to `UpdatePersonalInfoRequest`, and re-verified: the form now saves the flag and the server returns `is_gift_aid: true`.

The blast radius was wider than this slice. Any user who has ever ticked the box has had it silently dropped, so every Gift Aid calculation downstream, the band extension included, has been running as though they do not claim it. Worth a thought about existing accounts.

### 1. The childcare spend and the Gift Aid figure cannot be captured on the free tier — CLOSED for the walk

Severity: blocks three contract items. Confidence: high, verified live.

`users.childcare` and `users.charitable_donations` are both listed in `DETAILED_EXPENDITURE_FIELDS` at `app/Http/Controllers/Api/UserProfileController.php:39-59`, so a save containing either returns `capability_denied` for a user without `expenditure_detailed`. The frontend matches: `resources/js/components/UserProfile/ExpenditureForm.vue:1381` hides the Detailed View toggle unless `hasCapability('expenditure_detailed')`, leaving Simple View with a single monthly-total field. The live tier flags for user 416 read `"expenditure_detailed": "none"` on the free tier.

Two consequences. `ChildcareEntitlements::for()` at `app/Services/Tax/Thresholds/ChildcareEntitlements.php:39` requires `users.childcare > 0` before it emits the Tax-Free Childcare item, so that row can never appear for a free user; the funded-hours item still does, because it is computed from the child's age. And Gift Aid reaches the tax maths through `users.annual_charitable_donations`, which `app/Models/User.php:66-73` derives from the monthly column, so there is no route to a Gift Aid figure at all — not on web, not on `/m`, not through Fyn's capture form, because the gate is server-side.

Resolved for this walk by granting Premium through the product's own checkout, which is recorded above as test setup.
