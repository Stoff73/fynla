### 1. The "is this person my spouse" question has no named home (Rule 20 exposure)

**File:** `app/Services/Estate/UndividedShareDiscount.php:105`
**Category:** 6 — Inconsistency with existing patterns / Rule 20

The C2(c) fix introduced the app's **only** read of the raw `spouse_id` for a
relationship question, and it is an inline ternary buried in a valuation service:

```php
return $coOwnerId !== ($user->spouse_id === null ? null : (int) $user->spouse_id);
```

There are now three distinct spouse questions, and only two have a named home:

| Question | Named home | Soft-delete behaviour |
|---|---|---|
| May I show their data? | `User::liveSpouseId()` | null once deleted |
| May I attach a `joint_owner_id`? | `User::hasReciprocalSpouseLink()` | false once deleted |
| **Are these two married?** | **none — inline here** | must survive deletion |

Nineteen call sites use `liveSpouseId()`. The third question has one
implementation and no name, so the second consumer will copy the ternary rather
than find it — the precise disease Rule 20 names.

**There is a trap attached.** `hasReciprocalSpouseLink()` looks like the obvious
consolidation target and **is not**: its `static::query()->whereKey(...)->exists()`
runs under `User`'s `SoftDeletes` global scope (`User.php:29`), so a deleted
spouse account returns `false` and the discount switches back on over a spouse's
share — exactly the C2(c) defect this commit fixed. A future "tidy-up" onto that
method silently reintroduces an Inheritance Tax understatement, with no test
naming the reason.

**Suggested fix:** add a named `User` method for the relationship question —
`spouseIdRegardlessOfAccountState()` or similar — carrying the three-way
distinction above and an explicit "do not route this through
`hasReciprocalSpouseLink()`, it is soft-delete scoped" warning. Have `applies()`
call it. One line moves; the reasoning gets a home that survives the next reader.

### 1. The full test suite could not run at all — fatal redeclaration

**Files:** `tests/Feature/Goals/SharedGoalIsOneWholeGoalTest.php:34`,
`tests/Unit/Services/Estate/WillTypePolicyTest.php:15`
**Category:** 3 — convention violation, with a build-breaking consequence

W-0038's test declared a top-level `function linkedSpouses()`. That name was already
taken by `WillTypePolicyTest`. Pest includes every test file in a suite into one
process, so the two declarations met and PHP fataled **at collection**:

```
PHP Fatal error: Cannot redeclare linkedSpouses() ...
```

Not one failing test — **zero tests ran**. `./vendor/bin/pest` on `dev` was dead from
the moment #727 merged this morning until this pass.

**Why CI was green anyway, which is the more important half.** `.github/workflows/quality.yml:97`
runs `./vendor/bin/pest --testsuite=${{ matrix.suite }}` across a
`[Architecture, Unit, Feature, Integration, Eval]` matrix. `WillTypePolicyTest` is Unit
and `SharedGoalIsOneWholeGoalTest` is Feature, so the two names are **never loaded into
the same process on CI**. The shard boundary hides this entire class of defect, and it
will hide the next one identically. Anyone running the documented command from
`CLAUDE.md` — plain `./vendor/bin/pest` — hits a fatal that every PR check calls green.

**Fixed in this pass**, because a mainline that cannot run its tests is not an audit
finding to hand over:
- Helper renamed to `spousesLinkedForSharedGoal()`, with a docblock recording the
  collision, the CI blind spot, and why helper names must be specific.
- Swept the rest: **471 distinct top-level test helpers, no remaining duplicates.**

**Not fixed, and worth CSJ's view:** the sharding hole itself. A cheap guard is one
CI step that loads every test file in a single process — even `--collect-only`-style —
so a redeclaration is caught by the thing that is supposed to catch it.
