### 1. The "is this person my spouse" question has no named home (Rule 20 exposure)

**File:** `app/Services/Estate/UndividedShareDiscount.php:105`
**Category:** 6 — Inconsistency with existing patterns / Rule 20

The C2(c) fix introduced the app's **only** read of the raw `spouse_id` for a
relationship question, and it is an inline ternary buried in a valuation service:

```php
return $coOwnerId !== ($user->spouse_id === null ? null : (int) $user->spouse_id);
```

There are now three distinct spouse questions, and only two have a named home:

| Question | Named home | Soft-delete behaviour |
|---|---|---|
| May I show their data? | `User::liveSpouseId()` | null once deleted |
| May I attach a `joint_owner_id`? | `User::hasReciprocalSpouseLink()` | false once deleted |
| **Are these two married?** | **none — inline here** | must survive deletion |

Nineteen call sites use `liveSpouseId()`. The third question has one
implementation and no name, so the second consumer will copy the ternary rather
than find it — the precise disease Rule 20 names.

**There is a trap attached.** `hasReciprocalSpouseLink()` looks like the obvious
consolidation target and **is not**: its `static::query()->whereKey(...)->exists()`
runs under `User`'s `SoftDeletes` global scope (`User.php:29`), so a deleted
spouse account returns `false` and the discount switches back on over a spouse's
share — exactly the C2(c) defect this commit fixed. A future "tidy-up" onto that
method silently reintroduces an Inheritance Tax understatement, with no test
naming the reason.

**Suggested fix:** add a named `User` method for the relationship question —
`spouseIdRegardlessOfAccountState()` or similar — carrying the three-way
distinction above and an explicit "do not route this through
`hasReciprocalSpouseLink()`, it is soft-delete scoped" warning. Have `applies()`
call it. One line moves; the reasoning gets a home that survives the next reader.
