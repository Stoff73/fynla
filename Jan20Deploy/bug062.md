## BUG-001: Investment Dashboard Strategy Card Not Showing

**Date:** 20 January 2026
**Severity:** Medium
**Status:** Fixed

### Description

The Strategy card on the Investment Dashboard was not displaying for preview personas (and potentially real users). The card should show personalised investment recommendations when actionable insights exist.

### Root Cause

The recommendation generation thresholds in `InvestmentAgent.php` were too stringent. Preview personas had portfolios that were "too well optimised" according to the original rules, so no recommendations were generated and the Strategy card didn't appear.

Original thresholds:
- Diversification score < 60 to trigger recommendation
- Fee savings > £100 to trigger recommendation
- Tax efficiency score < 70 to trigger recommendation
- High-fee holdings threshold: 0.75% OCF

### Fix

Adjusted thresholds to be more realistic and added a new recommendation type:

| Threshold | Before | After |
|-----------|--------|-------|
| Diversification score | < 60 | < 70 |
| Fee savings | > £100 | > £50 |
| Tax efficiency score | < 70 | < 80 |
| High-fee holding | 0.75% | 0.5% |
| High-fee holdings check | N/A | **NEW** |

### Files Changed

```
app/Agents/InvestmentAgent.php
app/Services/Investment/FeeAnalyzer.php
```

### Code Changes

**`app/Agents/InvestmentAgent.php`** - `generateRecommendations()` method:

1. Changed diversification threshold from `< 60` to `< 70`
2. Changed fee savings threshold from `> 100` to `> 50`
3. Added new "High-Fee Holdings" recommendation:
   ```php
   // High-fee holdings recommendation (any holding with OCF > 0.5%)
   if (isset($analysis['fee_analysis']['high_fee_holdings']) && count($analysis['fee_analysis']['high_fee_holdings']) > 0) {
       $count = count($analysis['fee_analysis']['high_fee_holdings']);
       $recommendations[] = [
           'category' => 'High Fees',
           'priority' => $priority++,
           'title' => 'Review High-Fee Holdings',
           'description' => "You have {$count} holding(s) with fees above 0.5%. Consider lower-cost alternatives.",
           'action' => 'Compare fund fees and switch to low-cost index alternatives where appropriate',
       ];
   }
   ```
4. Changed tax efficiency threshold from `< 70` to `< 80`

**`app/Agents/InvestmentAgent.php`** - `analyze()` method:

Added high-fee holdings to fee analysis:
```php
$highFeeHoldings = $this->feeAnalyzer->identifyHighFeeHoldings($holdings);
$feeAnalysis['high_fee_holdings'] = $highFeeHoldings['holdings'];
```

**`app/Services/Investment/FeeAnalyzer.php`** - `identifyHighFeeHoldings()` method:

Changed threshold from 0.75% to 0.5%:
```php
$highFeeThreshold = 0.5; // 0.5% OCF is considered high (above passive index fund range)
```

2. Re-seeded preview users: `php artisan db:seed --class=PreviewUserSeeder --force`
3. Verified API returns recommendations:
   ```bash

   ```
   Returns: `"recommendation_count":4`
4. Verified Strategy card displays on Investment Dashboard with 4 recommendations
5. All unit tests pass: `./vendor/bin/pest tests/Unit/Services/Investment/`

## BUG-003: Risk Tab Detail View Back Button Goes to Investments Instead of Risk Dashboard

**Date:** 20 January 2026
**Severity:** Medium
**Status:** Fixed

### Description

When viewing the Risk tab in Valuable Info section, clicking into any detail view (e.g., risk factor details, risk levels explained) and then clicking the back button navigates to the Investment module instead of returning to the Risk tab dashboard view.

**Expected behavior:** Back button should return to wherever the user came from (Valuable Info Risk tab OR Risk Profile page).
**Actual behavior:** Back button was hardcoded to navigate to `/risk-profile` or `/net-worth/investments`.

### Root Cause

Two issues combined:

1. **Detail pages had hardcoded back destinations**: The Risk detail pages (`RiskFactorDetailPage.vue` and `RiskLevelsExplainedPage.vue`) had back buttons using hardcoded `router-link` to `/risk-profile`.

2. **ValuableInfo tabs didn't update URL**: When clicking tabs in `ValuableInfo.vue`, the URL stayed at `/valuable-info` without a `?section=risk` parameter. This meant browser history didn't know which tab you were on.

### Fix

**Part 1: Update detail pages to use `$router.back()`**

Changed back buttons from hardcoded `router-link` to buttons that use browser history:

```vue
<button @click="goBack" class="...">Back</button>
```

```javascript
goBack() {
  this.$router.back();
}
```

**Part 2: Update ValuableInfo.vue to sync URL with active tab**

Added URL synchronization so clicking tabs updates the URL query parameter:

```javascript
import { useRouter, useRoute } from 'vue-router';

// In setup()
const router = useRouter();
const route = useRoute();

// Update URL when tab changes
watch(activeTab, (newTab) => {
  const currentSection = route.query.section;
  if (currentSection !== newTab) {
    router.replace({ query: { section: newTab } });
  }
});
```

Now when user clicks Risk tab, URL becomes `/valuable-info?section=risk`, so `$router.back()` correctly returns to the Risk tab.

### Files Changed

```
resources/js/views/Risk/RiskFactorDetailPage.vue
resources/js/views/Risk/RiskLevelsExplainedPage.vue
resources/js/views/ValuableInfo.vue
```

3. Click Back button → Should return to Valuable Info Risk tab
4. Navigate to Risk Profile page directly (`/risk-profile`)

## BUG-008: Date of Birth Validation Missing Across Application

**Date:** 20 January 2026
**Severity:** Medium
**Status:** Fixed

### Description

Date of birth fields across the application lacked proper validation:

1. Users could enter future dates as date of birth
2. Users could enter dates older than 105 years
3. Primary users should be required to be 18+ years old
4. Spouses should be required to be 16+ years old (legal marriage age in UK)
5. Children should be max 22 years if in education, max 18 years if not in education
6. Other family members (parent, other dependent) can be any valid age (0-105)

### Root Cause

The frontend Vue components only had basic HTML5 date inputs without proper min/max constraints, and the backend Laravel validation only checked `before:today` without relationship-specific age validation.

### Fix

#### Frontend Changes

**1. PersonalInfoStep.vue (Onboarding)**
- Already had `maxDob` (18 years ago)
- Added `minDob` (105 years ago)
- Added `:min` attribute to date input

**2. PersonalInformation.vue (Profile Edit)**
- Added `maxDob` (18 years ago - user must be 18+)
- Added `minDob` (105 years ago)
- Added `:max` and `:min` attributes to date input

**3. FamilyMemberFormModal.vue (Family Members)**
- Added `minDob` (105 years ago)
- Added `maxDobForRelationship` computed property:
  - Spouse: 16 years ago (must be 16+)
  - Child/Step Child: depends on education status
    - In education: 22 years ago (max 22)
    - Not in education: 18 years ago (max 18)
  - Other: today (any age)
- Added `validateDob()` function with detailed error messages
- Added validation check in `handleSubmit()`

#### Backend Changes

**4. UpdatePersonalInfoRequest.php**
- Changed `before:today` to `before_or_equal:` + 18 years ago
- Added `after:` + 105 years ago
- Updated error messages

**5. StoreFamilyMemberRequest.php**
- Added `before_or_equal:today`, `after:` + 105 years ago
- Added `withValidator()` method with relationship-specific validation:
  - Spouse: age < 16 → error
  - Child/Step Child: age > 22 (education) or age > 18 (no education) → error
- Updated error messages

**6. UpdateFamilyMemberRequest.php**
- Same changes as StoreFamilyMemberRequest
- Gets relationship/education_status from request or existing family member record

## UI-014: Hide Complete Setup Button for Preview Users

**Date:** 20 January 2026
**Severity:** Medium (Bug Fix)
**Status:** Fixed

### Description

Preview users were seeing a "Complete Setup" button in the navigation which, when clicked, caused a 400 error on `/api/onboarding/steps` because preview users don't have `onboarding_focus_area` set in the database.

### Root Cause

The `showCompleteSetupButton` computed property in Navbar.vue didn't check for preview users. Preview users have `is_preview_user=true` and don't have onboarding data set.

### Fix

Updated the `showCompleteSetupButton` computed property to return `false` for preview users.

### Files Changed

```
resources/js/components/Navbar.vue
```

### Code Changes

Before:
```javascript
const showCompleteSetupButton = computed(() => {
  const user = store.getters['auth/currentUser'];
  if (!user?.onboarding_completed) {
    return true;
  }
  const skippedSteps = user?.onboarding_skipped_steps;
  return Array.isArray(skippedSteps) && skippedSteps.length > 0;
});
```

After:
```javascript
const showCompleteSetupButton = computed(() => {
  const user = store.getters['auth/currentUser'];
  if (!user) return false;
  // Never show for preview users
  if (user.is_preview_user) return false;
  if (!user.onboarding_completed) {
    return true;
  }
  const skippedSteps = user?.onboarding_skipped_steps;
  return Array.isArray(skippedSteps) && skippedSteps.length > 0;
});
```

### Testing

1. Login as any preview persona
2. Verify "Complete Setup" button does NOT appear in the navigation
3. No 400 errors on `/api/onboarding/steps`
