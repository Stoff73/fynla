## BUG-001: Investment Dashboard Strategy Card Not Showing

**Date:** 20 January 2026
**Severity:** Medium
**Status:** Fixed

### Description

The Strategy card on the Investment Dashboard was not displaying for preview personas (and potentially real users). The card should show personalised investment recommendations when actionable insights exist.

### Root Cause

The recommendation generation thresholds in `InvestmentAgent.php` were too stringent. Preview personas had portfolios that were "too well optimised" according to the original rules, so no recommendations were generated and the Strategy card didn't appear.

Original thresholds:
- Diversification score < 60 to trigger recommendation
- Fee savings > £100 to trigger recommendation
- Tax efficiency score < 70 to trigger recommendation
- High-fee holdings threshold: 0.75% OCF

### Fix

Adjusted thresholds to be more realistic and added a new recommendation type:

| Threshold | Before | After |
|-----------|--------|-------|
| Diversification score | < 60 | < 70 |
| Fee savings | > £100 | > £50 |
| Tax efficiency score | < 70 | < 80 |
| High-fee holding | 0.75% | 0.5% |
| High-fee holdings check | N/A | **NEW** |

### Files Changed

```
app/Agents/InvestmentAgent.php
app/Services/Investment/FeeAnalyzer.php
```

### Code Changes

**`app/Agents/InvestmentAgent.php`** - `generateRecommendations()` method:

1. Changed diversification threshold from `< 60` to `< 70`
2. Changed fee savings threshold from `> 100` to `> 50`
3. Added new "High-Fee Holdings" recommendation:
   ```php
   // High-fee holdings recommendation (any holding with OCF > 0.5%)
   if (isset($analysis['fee_analysis']['high_fee_holdings']) && count($analysis['fee_analysis']['high_fee_holdings']) > 0) {
       $count = count($analysis['fee_analysis']['high_fee_holdings']);
       $recommendations[] = [
           'category' => 'High Fees',
           'priority' => $priority++,
           'title' => 'Review High-Fee Holdings',
           'description' => "You have {$count} holding(s) with fees above 0.5%. Consider lower-cost alternatives.",
           'action' => 'Compare fund fees and switch to low-cost index alternatives where appropriate',
       ];
   }
   ```
4. Changed tax efficiency threshold from `< 70` to `< 80`

**`app/Agents/InvestmentAgent.php`** - `analyze()` method:

Added high-fee holdings to fee analysis:
```php
$highFeeHoldings = $this->feeAnalyzer->identifyHighFeeHoldings($holdings);
$feeAnalysis['high_fee_holdings'] = $highFeeHoldings['holdings'];
```

**`app/Services/Investment/FeeAnalyzer.php`** - `identifyHighFeeHoldings()` method:

Changed threshold from 0.75% to 0.5%:
```php
$highFeeThreshold = 0.5; // 0.5% OCF is considered high (above passive index fund range)
```

2. Re-seeded preview users: `php artisan db:seed --class=PreviewUserSeeder --force`
3. Verified API returns recommendations:

## BUG-003: Risk Tab Detail View Back Button Goes to Investments Instead of Risk Dashboard

**Date:** 20 January 2026
**Severity:** Medium
**Status:** Fixed

### Description

When viewing the Risk tab in Valuable Info section, clicking into any detail view (e.g., risk factor details, risk levels explained) and then clicking the back button navigates to the Investment module instead of returning to the Risk tab dashboard view.

**Expected behavior:** Back button should return to wherever the user came from (Valuable Info Risk tab OR Risk Profile page).
**Actual behavior:** Back button was hardcoded to navigate to `/risk-profile` or `/net-worth/investments`.

### Root Cause

Two issues combined:

1. **Detail pages had hardcoded back destinations**: The Risk detail pages (`RiskFactorDetailPage.vue` and `RiskLevelsExplainedPage.vue`) had back buttons using hardcoded `router-link` to `/risk-profile`.

2. **ValuableInfo tabs didn't update URL**: When clicking tabs in `ValuableInfo.vue`, the URL stayed at `/valuable-info` without a `?section=risk` parameter. This meant browser history didn't know which tab you were on.

### Fix

**Part 1: Update detail pages to use `$router.back()`**

Changed back buttons from hardcoded `router-link` to buttons that use browser history:

```vue
<button @click="goBack" class="...">Back</button>
```

```javascript
goBack() {
  this.$router.back();
}
```

**Part 2: Update ValuableInfo.vue to sync URL with active tab**

Added URL synchronization so clicking tabs updates the URL query parameter:

```javascript
import { useRouter, useRoute } from 'vue-router';

// In setup()
const router = useRouter();
const route = useRoute();

// Update URL when tab changes
watch(activeTab, (newTab) => {
  const currentSection = route.query.section;
  if (currentSection !== newTab) {
    router.replace({ query: { section: newTab } });
  }
});
```

Now when user clicks Risk tab, URL becomes `/valuable-info?section=risk`, so `$router.back()` correctly returns to the Risk tab.

### Files Changed

```

resources/js/views/Risk/RiskLevelsExplainedPage.vue
resources/js/views/ValuableInfo.vue
```

3. Click Back button → Should return to Valuable Info Risk tab
4. Navigate to Risk Profile page directly (`/risk-profile`)

## BUG-010: Child Date of Birth Validation Inverted

**Date:** 20 January 2026
**Severity:** Medium
**Status:** Fixed

### Description

When adding a child family member, valid dates of birth (like 2010 for a 16-year-old) were being blocked by the date picker. The validation logic was inverted - it set `max` to 18/22 years ago instead of `min`.

**Expected behavior:**
- Child (not in education): can be 0-18 years old (DOB from 18 years ago to today)
- Child (in education): can be 0-22 years old (DOB from 22 years ago to today)

**Actual behavior:**
- The date picker `max` attribute was set to 18/22 years ago, blocking any date after that (including valid younger children)

### Root Cause

The `maxDobForRelationship` computed property incorrectly calculated the child's DOB constraint. For children, the oldest DOB allowed (18/22 years ago) should be the `min`, not the `max`. The `max` should be today (newborns are valid).

### Fix

Refactored both `minDob` and `maxDobForRelationship` computed properties to be relationship-aware:

**New logic:**

| Relationship | Min DOB | Max DOB |
|-------------|---------|---------|
| Child (not in education) | 18 years ago | today |
| Child (in education) | 22 years ago | today |
| Spouse | 105 years ago | 16 years ago |
| Parent/Other | 105 years ago | today |

## BUG-006: Joint Ownership Not Using Correct Percentage in Balance Sheet and Estate Planning

**Date:** 20 January 2026
**Severity:** High
**Status:** Fixed

### Description

Two related issues with joint/tenants_in_common ownership:

1. **Balance Sheet (Valuable Info)**: Properties and mortgages with joint or tenants_in_common ownership were hardcoded to 50% split instead of using the actual `ownership_percentage`. A 30/70 tenants_in_common property showed £250,000 for both users instead of £150,000/£350,000.

2. **Estate Planning IHT**: Joint mortgages only showed under the primary owner with full balance. The spouse saw £0 liabilities.

### Root Cause

**PersonalAccountsService.php** (Balance Sheet):
- Hardcoded `* 0.5` for all joint ownership instead of using `ownership_percentage`
- Didn't handle `tenants_in_common` ownership type
- Example of buggy code:

```php
if ($property->ownership_type === 'joint' && $property->joint_owner_id) {

}
```

**IHTController.php** (Estate Planning):
- Query only checked `user_id`, missing mortgages where user is `joint_owner_id`
- Used full balance without applying ownership percentage

```php
$amount = $property->current_value;
if ($property->ownership_type === 'joint' && $property->joint_owner_id) {
```

```php
// Before (only primary owner):
$userMortgages = Mortgage::where('user_id', $user->id)->get();

    $query->where('user_id', $user->id)
          ->orWhere('joint_owner_id', $user->id);
```

## BUG-006-DUPLICATE: Joint Mortgage Not Showing in Spouse's Estate Planning Liabilities

**Note:** This was merged into BUG-006 above as they share the same root cause.

**Date:** 20 January 2026
**Severity:** High
**Status:** Fixed

### Description

In Estate Planning's IHT Calculation (Joint Death Scenario), joint mortgages were showing the full mortgage balance under the primary owner only, with the spouse showing £0 liabilities. For a £200,000 mortgage owned 50/50, Chris showed -£200,000 and Angela showed £0 instead of both showing -£100,000.

### Root Cause

The `formatLiabilitiesBreakdown()` method in `IHTController.php` had two issues:

1. **Query only checked primary owner**: `Mortgage::where('user_id', $user->id)` missed mortgages where the user is the joint owner (`joint_owner_id`)

2. **Used full balance without ownership share**: `$mortgage->outstanding_balance` was used directly instead of calculating the user's share based on `ownership_percentage`

Additionally, the `Mortgage` model was missing `ownership_percentage` in both `$fillable` and `$casts` arrays, preventing proper saving/updating of this field.

### Fix

1. **Updated mortgage query** to include mortgages where user is joint owner:

```php
// Before:
$userMortgages = Mortgage::where('user_id', $user->id)->with('property')->get();

// After:
$userMortgages = Mortgage::where(function ($query) use ($user) {
    $query->where('user_id', $user->id)
          ->orWhere('joint_owner_id', $user->id);
})->with('property')->get();
```

2. **Applied ownership share calculation** using `CalculatesOwnershipShare` trait:

```php
// Before:
$userMortgagesFormatted[] = [
    'outstanding_balance' => $mortgage->outstanding_balance,  // Full balance
    // ...
];
$userMortgagesTotal += $mortgage->outstanding_balance;

// After:
$userShare = $this->calculateUserMortgageShare($mortgage, $user->id);
$userMortgagesFormatted[] = [
    'outstanding_balance' => $userShare,  // User's share
    'full_balance' => (float) $mortgage->outstanding_balance,
    'ownership_percentage' => $isJoint ? ($mortgage->user_id === $user->id ? $mortgage->ownership_percentage : (100 - $mortgage->ownership_percentage)) : 100,
    // ...
];
$userMortgagesTotal += $userShare;
```

3. **Added `ownership_percentage` to Mortgage model** `$fillable` and `$casts` arrays

4. **Added backend safeguard in PropertyController** to default joint mortgage `ownership_percentage` to 50% if it's 100%

## BUG-007: 2FA Prompts Not Disappearing After Enabling MFA

**Date:** 20 January 2026
**Severity:** Medium
**Status:** Fixed

### Description
When a user enables two-factor authentication (2FA), the prompts to enable 2FA on the dashboard banner and navigation bar were still showing. These should disappear once MFA is enabled.

### Root Cause
When MFA was enabled/disabled in `SecuritySettings.vue`, the component only updated its local `mfaEnabled` state. The user object in the Vuex auth store was not being refreshed, so components checking `user.mfa_enabled` (Navbar and Dashboard) still saw the old value.

### Fix
After enabling or disabling MFA, dispatch `auth/fetchUser` to refresh the user object in the Vuex store.

```javascript
// Before:
onMFAEnabled() {
  this.mfaEnabled = true;
  this.showMFASetupModal = false;
}

// After:
async onMFAEnabled() {
  this.mfaEnabled = true;
  this.showMFASetupModal = false;
  // Update user in Vuex store so navbar/dashboard hide the 2FA prompts
  await this.$store.dispatch('auth/fetchUser');
}
```

Same fix applied to `disableMFA()` method.
