## BUG-001: Investment Dashboard Strategy Card Not Showing

**Date:** 20-21 January 2026
**Severity:** Medium
**Status:** Fixed

### Description

The Strategy card on the Investment Dashboard was not displaying for users. The card should show personalised investment recommendations when actionable insights exist.

### Root Cause

Two issues identified:

1. **Initial fix (20 Jan):** Recommendation thresholds were too stringent for users with holdings
2. **Final fix (21 Jan):** ALL recommendations required either holdings data OR a risk profile. Users without these got NO recommendations, so the Strategy card never appeared.

### Fix

**Phase 1 (20 Jan):** Adjusted thresholds for users with holdings:

| Threshold | Before | After |
|-----------|--------|-------|
| Diversification score | < 60 | < 70 |
| Fee savings | > £100 | > £50 |
| Tax efficiency score | < 70 | < 80 |
| High-fee holding | 0.75% | 0.5% |

**Phase 2 (21 Jan):** Added recommendations that trigger WITHOUT holdings or risk profile:

```php
// No risk profile recommendation - always show if not set
if (! $hasRiskProfile) {
    $recommendations[] = [
        'category' => 'Risk Profile',
        'priority' => $priority++,
        'title' => 'Complete Your Risk Profile',
        'description' => 'Set up your risk profile to get personalised investment recommendations and target allocations.',
        'action' => 'Complete the risk questionnaire to determine your investment strategy',
    ];
}

// No holdings recommendation - show if accounts exist but no holdings
if ($holdingsCount === 0 && ($analysis['portfolio_summary']['accounts_count'] ?? 0) > 0) {
    $recommendations[] = [
        'category' => 'Portfolio Setup',
        'priority' => $priority++,
        'title' => 'Add Your Holdings',
        'description' => 'Add your fund holdings to get detailed fee analysis, diversification scores, and tax efficiency recommendations.',
        'action' => 'Click on your investment account and add your holdings',
    ];
}
```

### Files Changed

```
app/Agents/InvestmentAgent.php
app/Services/Investment/FeeAnalyzer.php
```

### Testing

1. User with no risk profile and no holdings: Strategy card shows "Complete Your Risk Profile" and "Add Your Holdings"
2. User with risk profile but no holdings: Strategy card shows "Add Your Holdings"
3. User with holdings and risk profile: Strategy card shows relevant recommendations (fees, diversification, rebalancing, etc.)

## BUG-003: Risk Tab Detail View Back Button Goes to Investments Instead of Risk Dashboard

**Date:** 20 January 2026
**Severity:** Medium
**Status:** Fixed

### Description

When viewing the Risk tab in Valuable Info section, clicking into any detail view (e.g., risk factor details, risk levels explained) and then clicking the back button navigates to the Investment module instead of returning to the Risk tab dashboard view.

**Expected behavior:** Back button should return to wherever the user came from (Valuable Info Risk tab OR Risk Profile page).
**Actual behavior:** Back button was hardcoded to navigate to `/risk-profile` or `/net-worth/investments`.

### Root Cause

Two issues combined:

1. **Detail pages had hardcoded back destinations**: The Risk detail pages (`RiskFactorDetailPage.vue` and `RiskLevelsExplainedPage.vue`) had back buttons using hardcoded `router-link` to `/risk-profile`.

2. **ValuableInfo tabs didn't update URL**: When clicking tabs in `ValuableInfo.vue`, the URL stayed at `/valuable-info` without a `?section=risk` parameter. This meant browser history didn't know which tab you were on.

### Fix

**Part 1: Update detail pages to use `$router.back()`**

Changed back buttons from hardcoded `router-link` to buttons that use browser history:

```vue
<button @click="goBack" class="...">Back</button>
```

```javascript
goBack() {
  this.$router.back();
}
```

**Part 2: Update ValuableInfo.vue to sync URL with active tab**

Added URL synchronization so clicking tabs updates the URL query parameter:

```javascript
import { useRouter, useRoute } from 'vue-router';

// In setup()
const router = useRouter();
const route = useRoute();

// Update URL when tab changes
watch(activeTab, (newTab) => {
  const currentSection = route.query.section;
  if (currentSection !== newTab) {
    router.replace({ query: { section: newTab } });
  }
});
```

Now when user clicks Risk tab, URL becomes `/valuable-info?section=risk`, so `$router.back()` correctly returns to the Risk tab.

### Files Changed

```
resources/js/views/Risk/RiskFactorDetailPage.vue
resources/js/views/Risk/RiskLevelsExplainedPage.vue
resources/js/views/ValuableInfo.vue
```

### Testing

3. Click Back button → Should return to Valuable Info Risk tab
4. Navigate to Risk Profile page directly (`/risk-profile`)

## BUG-010: Child Date of Birth Validation Inverted

**Date:** 20 January 2026
**Severity:** Medium
**Status:** Fixed

### Description

When adding a child family member, valid dates of birth (like 2010 for a 16-year-old) were being blocked by the date picker. The validation logic was inverted - it set `max` to 18/22 years ago instead of `min`.

**Expected behavior:**
- Child (not in education): can be 0-18 years old (DOB from 18 years ago to today)
- Child (in education): can be 0-22 years old (DOB from 22 years ago to today)

**Actual behavior:**
- The date picker `max` attribute was set to 18/22 years ago, blocking any date after that (including valid younger children)

### Root Cause

The `maxDobForRelationship` computed property incorrectly calculated the child's DOB constraint. For children, the oldest DOB allowed (18/22 years ago) should be the `min`, not the `max`. The `max` should be today (newborns are valid).

### Fix

Refactored both `minDob` and `maxDobForRelationship` computed properties to be relationship-aware:

**New logic:**

| Relationship | Min DOB | Max DOB |
|-------------|---------|---------|
| Child (not in education) | 18 years ago | today |
| Child (in education) | 22 years ago | today |
| Spouse | 105 years ago | 16 years ago |
| Parent/Other | 105 years ago | today |

### Files Changed

```
resources/js/components/UserProfile/FamilyMemberFormModal.vue
```

### Code Changes

```javascript
// Date constraints - both min and max depend on relationship
const minDob = computed(() => {
  const date = new Date();

  if (form.value.relationship === 'child' || form.value.relationship === 'step_child') {
    // Child: oldest allowed is 18 or 22 years ago depending on education
    const educationStatuses = ['pre_school', 'primary', 'secondary', 'further_education', 'higher_education'];
    const isInEducation = educationStatuses.includes(form.value.education_status);
    const maxAge = isInEducation ? 22 : 18;
    date.setFullYear(date.getFullYear() - maxAge);
    return date.toISOString().split('T')[0];
  }

  // All others: max age 105 years
  date.setFullYear(date.getFullYear() - 105);
  return date.toISOString().split('T')[0];
});

const maxDobForRelationship = computed(() => {
  const today = new Date();

  if (form.value.relationship === 'spouse') {
    // Spouse must be 16+ (born at least 16 years ago)
```

## BUG-014: Monte Carlo Charts Starting at Wrong Values and Year

**Date:** 21 January 2026
**Severity:** Medium
**Status:** Fixed

### Description

The Monte Carlo projection charts for both Investments and Retirement were:
1. Starting at 2027 instead of 2026 (current year)
2. Each probability band starting at a different value instead of all starting at the current portfolio value

### Root Cause

The `extractProbabilityBands` method in both `InvestmentProjectionService.php` and `RetirementProjectionService.php` was iterating only through the Monte Carlo simulation results, which start from year 1 (already with diverging values due to random returns). There was no "year 0" entry representing the current year with the current value.

### Fix

Added a year 0 entry at the beginning of the `extractProbabilityBands` method in both services. This entry uses:
- `year` = current year (2026)
- `year_number` = 0
- All percentiles = current portfolio/pension value (same for all bands)

This ensures all probability bands converge at the starting point (current value) and then diverge from year 1 onwards.

### Files Changed

```
app/Services/Investment/InvestmentProjectionService.php
app/Services/Retirement/RetirementProjectionService.php
```

### Code Changes

**Part 1: Add year 0 entry** - Added to both `extractProbabilityBands` methods:

```php
$startValue = $simulation['summary']['start_value'] ?? 0;

// Add year 0 (current year) with current value - all bands start at the same point
$result[] = [
    'year' => $currentYear,
    'year_number' => 0,
    'percentile_5' => round($startValue, 2),
    'percentile_10' => round($startValue, 2),
    'percentile_15' => round($startValue, 2),
    'percentile_20' => round($startValue, 2),
    'percentile_50' => round($startValue, 2),
    'percentile_75' => round($startValue, 2),
    'percentile_90' => round($startValue, 2),
];
```

**Part 2: Smooth transition blending** - After adding year 0, the chart showed a V-shape where lower percentiles dropped below the start value in year 1 before climbing back up. Fixed by blending early years with the start value for smooth divergence:

```php
// Smooth transition for early years - blend with start value
// Year 1: 70% Monte Carlo, 30% start value
// Year 2: 90% Monte Carlo, 10% start value
// Year 3+: 100% Monte Carlo
$blendFactor = 1.0;
if ($yearIndex === 1) {
    $blendFactor = 0.7;
} elseif ($yearIndex === 2) {
    $blendFactor = 0.9;
}

$p5 = $this->blendValue($p5, $startValue, $blendFactor);
$p10 = $this->blendValue($p10, $startValue, $blendFactor);
// ... all percentiles blended

// Helper method added:
private function blendValue(float $monteCarloValue, float $startValue, float $blendFactor): float
{
    return ($monteCarloValue * $blendFactor) + ($startValue * (1 - $blendFactor));
}
```

## FEATURE-001: Password Reset Functionality

**Date:** 21 January 2026
**Severity:** Feature
**Status:** Implemented

### Description

Added "Forgot Password" functionality to the login screen using email verification codes. Users with MFA enabled must also verify their MFA (TOTP or recovery code) before resetting their password.

### Security Features

- **Non-MFA users**: Email verification code only (proves email ownership)
- **MFA users**: Email verification + MFA code (defense in depth)
- Token-based session tracking (64-char token, never exposes user_id to frontend)
- Account enumeration prevention (always returns success for email requests)
- 15-minute session expiry, single-use tokens
- Maximum 2 code resends per session
- All existing tokens revoked on password reset
- Audit logging for security events

### User Flows

**Non-MFA User:**
1. Click "Forgot password?" → Enter email → Receive code
2. Enter 6-digit code → Enter new password → Success

**MFA User:**
1. Click "Forgot password?" → Enter email → Receive code
2. Enter 6-digit code → Enter TOTP (or recovery code) → Enter new password → Success

### API Endpoints

| Endpoint | Rate Limit | Description |
|----------|------------|-------------|
| `POST /auth/password-reset/request` | 3/min | Initiate password reset |
| `POST /auth/password-reset/verify-email` | 10/min | Verify email code |
| `POST /auth/password-reset/resend-code` | 5/min | Resend verification code |
| `POST /auth/password-reset/verify-mfa` | 10/min | Verify MFA TOTP code |
| `POST /auth/password-reset/mfa-recovery` | 5/min | Use recovery code |
| `POST /auth/password-reset/reset` | 5/min | Reset password |
