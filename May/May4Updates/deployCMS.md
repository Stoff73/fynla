# Document Articles CMS — Deployment Guide

Generated 4 May 2026 from `git diff` against `origin/dev` and `origin/main`.

This guide ships the **Document Articles CMS** feature on branch `CMSFix`. It does **not** cover unrelated work that may be merged in the same `dev → main` PR (see "What ships with the prod merge" below).

---

## What's being deployed

A `.docx` upload pipeline that converts Word documents to sanitised HTML articles and exposes them at public `/articles/{slug}` URLs.

- Admin UI at `/admin/documents` — list, drag-drop import, edit, publish/unpublish, delete
- Public read at `/articles/{slug}` (Blade-rendered, full SEO chrome)
- One new database table: `document_articles`
- One new PHP dependency: `mews/purifier ^3.4`
- Ten new JS dependencies (8 Tiptap extensions + `mammoth` + `jszip`) — bundled into the Vite output, no server install
- New API routes under `/api/admin/documents` (auth + `permission:admin.access`) and `/articles/{slug}` (public)

## Pre-flight — DO BEFORE STARTING

1. **Pest must be green:** `./vendor/bin/pest tests/Unit/Services/Documents tests/Feature/Documents` should report 53 / 141 — already verified locally on `5fc22ee`.
2. **Editor blocker:** `resources/js/views/Admin/Documents/DocumentEditor.vue:80–83` uses `import Default from '@tiptap/extension-table*'` but those packages export only named bindings. The editor view **will crash** when an admin clicks "Edit" on a draft. Either:
   - **Fix first** — change to `import { Table } from '@tiptap/extension-table'` (and the three sibling table packages), rebuild, then deploy; **or**
   - **Ship knowingly** — drag-drop import + publish + public read all work; only the in-product editor view is broken. Drafts can still be published from the list page.
   This is your call. Flagging because it's a real defect on the branch you're deploying.
3. **Latent bootstrap.js axios baseURL** (`resources/js/bootstrap.js:27`) hardcodes `http://127.0.0.1:8000` regardless of which host loaded the page. Every existing service routes around it via `services/api.js`; the CMS service used to be the exception, fixed in `5fc22ee`. Not blocking — flagging for a separate cleanup.
4. **Branch up to date:** `git fetch origin && git log origin/CMSFix..HEAD` should be empty. Pushed at `5fc22ee`.

`public/build/` is regenerated by the build script. Upload the entire directory — Vite's content-hashed filenames mean partial uploads can leave dangling references.

## Rollback

### Application code

```bash
git checkout main
git revert <merge-commit-sha>   # creates a clean revert commit
git push
# Then re-run build + upload of the prior public/build/ if you saved it as build.old/
```

If you didn't save `build.old/`, build from the reverted main (`./deploy/fynla-org/build.sh`) and re-upload `public/build/`.

### Migration

`document_articles` is the only new table from this CMS work. To roll back the migration alone:

```bash
ssh -p 18765 -i ~/.ssh/production u2783-hrf1k8bpfg02@ssh.fynla.org
cd ~/www/fynla.org/public_html
php artisan migrate:rollback --step=1 --force   # CMS migration only — verify with: php artisan migrate:status | tail -5
```

**Do not** `php artisan migrate:fresh` or `migrate:refresh` — drops every table.

### Composer

The `mews/purifier` package is harmless to leave installed even after a code revert (no autoload-time side effects). Skip the composer rollback unless you're triaging a vendor conflict.
