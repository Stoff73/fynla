## 2. Test quality

### 2.1 Tests asserting nothing meaningful (severity: low, confidence: high)

`grep -rn "expect(true)->toBeTrue"` finds **9 occurrences**. All but one are paired with Mockery spies (`shouldHaveReceived` / `shouldNotHaveReceived`) — the `expect(true)` is just a Pest assertion-count placeholder. Specifically:

- `tests/Unit/Console/Commands/EvalRecordCommandResetOrchestrationTest.php:41, 51, 66, 86, 101` — paired with `$spy->shouldHaveReceived(...)` / `shouldNotHaveReceived(...)` calls **above** the `expect(true)`. The Mockery assertion is the real behavioural check. **Acceptable** but unidiomatic — prefer Pest's `Mockery::close()` in `afterEach` already runs verification, so the trailing `expect(true)` is a no-op. Could be removed.
- `tests/Unit/Services/Auth/SessionServiceTest.php:223, 229` — in **no-op tests** that only check no exception was thrown:
  ```php
  it('silently no-ops when current token is a TransientToken', function () {
      $this->user->withAccessToken(new TransientToken);
      $this->sessionService->updateCurrentSessionActivity($this->user);
      expect(true)->toBeTrue();
  });
  ```
  This is genuinely a "test asserting nothing meaningful" — no `assertDatabaseMissing`, no `expect(...)->not->toThrow(...)`. Suggest adding an assertion like `expect(UserSession::count())->toBe(0)`.
- `tests/Unit/Services/Coordination/CrossModuleStrategyServiceTest.php:289` — `expect(true)->toBeTrue();` is the **only** assertion in a test that uses `$this->fail(...)` to fail mid-loop. Acceptable pattern (early-fail via `$this->fail`), but flagged for visibility — the assertion would be clearer as `expect($strategies)->toBeInOrderByPriority()` (custom expectation).
- `tests/Feature/RetirementIntegrationTest.php:404` — needs inspection (not read).

Only **one** non-Browser `markTestSkipped` in the entire suite:
- `tests/Feature/Fyn/Eval/EvalHttpDriverTest.php:14-18` — skipped because it's a live-integration test requiring `./dev.sh` running + real Anthropic key. The docblock references implementation-plan Task 10.4. **Acceptable** — labelled with clear instructions for manual invocation.

### 2.3 Tests that mock the thing they're testing / mock-heavy orchestration tests (severity: medium, confidence: medium)

**`tests/Unit/Agents/SavingsAgentTest.php`** (`beforeEach`, lines 17-39): mocks **every collaborator** of `SavingsAgent` (`EmergencyFundCalculator`, `ISATracker`, `GoalProgressCalculator`, `LiquidityAnalyzer`, `RateComparator`, `SavingsDataReadinessService`) and then asserts the agent passes their outputs through. This is structurally valid — but it means the test will **pass even if the agent silently broke an integration point** (e.g. forgot to call `categorizeAdequacy`). The test exercises ~0 real behaviour of `SavingsAgent` itself.

The integration test `tests/Integration/CrossModuleIntegrationTest.php` partly compensates by exercising real services together, but only at the data-readiness boundary.

**Same pattern** in `ProtectionAgentTest`, `GoalsAgentTest`, `ProtectionAgentGoalsTest`, `EstateAgentGoalsTest`, `SavingsAgentGoalsTest`, `RetirementAgentGoalsTest`. The `*GoalsTest` variants are particularly mock-heavy — they mock `TaxConfigService` (`grep -l "Mockery::mock(TaxConfigService" tests/Unit/Agents/`) to test goal-affordability flows.

**Recommendation:** For each agent, keep ONE mock-heavy test that pins the orchestration contract, and add ONE real-service test (with `RefreshDatabase` + seeded `TaxConfiguration`) that asserts on the actual numbers a real user would see. The `TaxStrategyCalculatorTest` pattern (line 21-23, real seeder) is the right model.

## 3. Pest conventions

### 3.1 Mixed Pest vs PHPUnit-class form (severity: medium, confidence: high)

**9 test files still use legacy PHPUnit-class syntax** (`class Foo extends TestCase` + `public function test_…()`):

- `tests/Unit/Services/MortgageServiceTest.php`
- `tests/Unit/Services/PropertyTaxServiceTest.php`
- `tests/Unit/Services/PropertyServiceTest.php`
- `tests/Unit/Services/TaxConfigServiceTest.php`
- `tests/Feature/Security/UserMassAssignmentTest.php`
- `tests/Feature/Api/MortgageControllerTest.php`
- `tests/Feature/Api/PropertyControllerTest.php`
- `tests/Feature/CrossModuleIntegrationTest.php`
- `tests/Feature/TaxConfigurationTest.php`

Per `tests/CLAUDE.md`: "Use `it()` / `describe()` syntax (not `test_` PHPUnit methods)." These files predate the convention.

**Recommendation:** Convert to Pest syntax. The functional change is mechanical — change `class FooTest extends TestCase { use RefreshDatabase; protected function setUp(): void {…} public function test_x(): void {…} }` to `uses(RefreshDatabase::class); beforeEach(function () {…}); it('x', function () {…});` — but read `Pest.php`'s `uses(…)->in('Feature', 'Unit/Services')` first, which already binds `RefreshDatabase` to those directories.

### 3.2 `Sanctum::actingAs` vs `actingAs` inconsistency (severity: low, confidence: high)

- 27 files use `Sanctum::actingAs($user)`
- 80 files use `actingAs($user)` (Laravel's default web-guard helper)

`tests/CLAUDE.md` says both are acceptable: "Auth: `$this->actingAs($user)` or `Sanctum::actingAs($user)`". But the canonical Fynla auth is Sanctum + session — using bare `actingAs` works for session auth, and `Sanctum::actingAs` works for API-token contexts. The mixed usage is mostly correct, but new tests should prefer `Sanctum::actingAs` for `/api/*` routes since that's what production uses.

**Recommendation:** Add a short comment in `tests/CLAUDE.md` clarifying when each is appropriate — current text is ambiguous.

### 3.3 `Mockery::close()` discipline — clean (severity: none, confidence: high)

**Every file** using `Mockery::mock` or `Mockery::spy` (51 files) also has `Mockery::close()` (55 files have the close call). Cleaner than expected. No teardown gaps.

### 3.4 `declare(strict_types=1)` — universal (severity: none, confidence: high)

Zero test files missing the declaration. **Clean.**

### 3.5 `RefreshDatabase` — wired via `Pest.php` (severity: none, confidence: high)

`Pest.php:19-44` binds `RefreshDatabase` to:
- All of `Feature/`
- `Unit/Services/`, `Unit/Observers/`
- The 7 listed `Unit/Agents/*Test.php` files that need DB
- `Integration/`

PHPUnit-class-form files (§3.1) still `use RefreshDatabase` manually. **Clean.**

### 3.6 `Pest.php` — global `beforeEach` only seeds when missing (severity: low, confidence: high)

`Pest.php:60-67` runs:
```php
if (! TaxConfiguration::where('is_active', true)->exists()) {
    TaxConfiguration::factory()->create(['is_active' => true]);
}
```
This conditionally seeds. It uses `TaxConfiguration::factory()` (not the seeder), so any test relying on the *full* tax-year set (`TaxConfigurationSeeder` seeds 5 years per `database/CLAUDE.md`) still needs to call `$this->seed(TaxConfigurationSeeder::class)` explicitly. Many tests do this, but the inconsistency is a footgun — a test author seeing the global beforeEach may assume the full seeder ran.

**Recommendation:** Either replace the conditional check with `$this->seed(TaxConfigurationSeeder::class)` (slower but predictable), or comment-document the divergence in `Pest.php`.

### 4.2 UserFactory missing canonical-enum default (severity: medium, confidence: high)

`database/factories/UserFactory.php:37` sets `'marital_status' => 'single'`. The BS-01 docblock explicitly notes this is a footgun:

> "Earlier 'stub gap' claim that base_personal couldn't capture marital was wrong: `User::factory()`'s default `marital_status='single'` (UserFactory:36) routes `buildPersonalPrompt` to its 'have you noted as single — share your DOB' branch. **Recommendation:** Change the default to `null` and add a `single()`, `married()` state method for tests that need it. This will catch a real class of bugs the BS-01 author already tripped over.
